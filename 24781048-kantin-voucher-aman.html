Kontrol Keamanan yang Diterapkan

Pertahanan Berlapis di Luar Model

Versi aman ini menerapkan kontrol di lapisan aplikasi, bukan hanya di teks system prompt. Ini penting karena model bahasa dapat tetap mengikuti instruksi berbahaya bahkan dengan larangan di prompt.

  • Hierarki Instruksi: System prompt menggunakan struktur peran (system/user) — input pengguna diperlakukan sebagai data, bukan instruksi.
  • Validasi Input (Pre-processing): Pesan pengguna diperiksa sebelum dikirim ke model. Override terdeteksi → ditolak di lapisan aplikasi.
  • Least Privilege: Fungsi buat_voucher dihapus dari akses chatbot. Kasir menggunakan sistem terpisah.
  • Kebijakan Voucher Eksplisit: Aturan voucher diterapkan di logika aplikasi, bukan hanya di teks prompt.
  • Tidak Bocorkan Instruksi: System prompt tidak ditampilkan kepada pengguna.
Kontrol 1: Hierarki Instruksi
Messages API dengan Peran Terpisah

System prompt berada di peran "system" yang terpisah dari "user". Model tahu mana instruksi pengembang dan mana input pengguna.

[ { "role": "system", ← instruksi tepercaya "content": "Kamu chatbot kantin. Jawab menu, harga, jam buka saja." }, { "role": "user", ← input tidak tepercaya (data) "content": "[INPUT PENGGUNA]" } ]
Kontrol 2: Validasi Input
Pre-processing Sebelum ke Model

Sebelum input pengguna dikirim ke model, aplikasi memeriksa pola override. Jika terdeteksi, permintaan ditolak tanpa memanggil model.

// Kontrol di lapisan aplikasi if (OVERRIDE_PATTERN.test(pesan)) { return { balasan: "Permintaan tidak dapat diproses.", aksi: [] }; // Model TIDAK dipanggil sama sekali }
Kontrol 3: Least Privilege
Fungsi Voucher Dihapus

Versi aman tidak memiliki fungsi buat_voucher. Bahkan jika model memintanya, aplikasi tidak akan mengeksekusinya karena tidak ada dalam allowlist.

// ALLOWLIST tool yang diizinkan chatbot const TOOL_ALLOWLIST = ["tanya_menu", "tanya_harga", "tanya_jadwal"]; // buat_voucher TIDAK ada → selalu ditolak otomatis const aksiTerfilter = (aksiDariModel || []) .filter(a => TOOL_ALLOWLIST.includes(a.tool)); // ← gerbang
Kontrol 4: Kebijakan Eksplisit
Aturan di Kode, Bukan Hanya di Teks

Aturan voucher diterapkan di logika JavaScript, bukan hanya di kalimat system prompt. Meski prompt berhasil diinjeksi, kode aplikasi tetap menolak voucher.

// Kebijakan voucher di lapisan aplikasi function cekKebijakan(balasan, aksi) { if (/VOUCHER/i.test(balasan) || aksi.some(a=>a.tool==="buat_voucher")) { return { aman: false, alasan: "Kebijakan voucher dilanggar" }; } return { aman: true }; }
Keterbatasan (Jujur): Tidak ada sistem yang 100% aman dari prompt injection. Penyerang yang cukup kreatif mungkin menemukan bypass terhadap pola yang digunakan. Tujuan pertahanan berlapis adalah membuat serangan jauh lebih sulit, bukan mustahil. Validasi di kode aplikasi lebih andal daripada bergantung pada model untuk "tahu" harus menolak.

Keterbatasan & Rekomendasi Lanjutan
Keterbatasan pola regex: Validasi berbasis regex dapat dibypass dengan variasi teks yang tidak terpola (misalnya penggunaan sinonim, karakter khusus, atau bahasa lain). Untuk sistem produksi, gunakan classifier khusus atau model terlatih untuk deteksi injeksi.
Keterbatasan model: Bahkan dengan hierarki peran (system/user), beberapa model LLM masih dapat terpengaruh oleh injeksi yang dikemas dengan baik. Pertahanan harus berlapis, bukan hanya mengandalkan satu kontrol.
Rekomendasi lanjutan: (1) Audit log secara berkala, (2) rate limiting pada endpoint chatbot, (3) monitoring anomali pada pola permintaan, (4) pengujian red-team secara rutin, (5) gunakan LLM Guard atau output validator untuk sistem produksi.
